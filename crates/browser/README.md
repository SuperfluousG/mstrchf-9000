# Browser domain boundary

Standalone Rust 1.94 crate with a separate pinned lockfile. It compiles the existing contracts/core and parameterises the pure planner from `crates/store/src/planner.rs` with an explicit immutable catalogue; `build.rs` retains the shared context constructor from `development.rs`. Frozen engineering-v1 premises and exact compiled maker packets own evidence. No second arithmetic, portion or scheduling engine is authored. It has no SQLite, Tauri, clock, network or filesystem runtime dependency, and needs no wasm-bindgen.

Build: `cargo build --manifest-path crates/browser/Cargo.toml --target wasm32-unknown-unknown --release --locked`.

Test: `cargo test --manifest-path crates/browser/Cargo.toml --release --locked --test browser`.

The module exports `memory`, `alloc(length)`, `dealloc(pointer,length)` and `run(pointer,length)`. `run` returns a JavaScript BigInt with the response pointer in the low 32 bits and its length in the high 32 bits. Both input and output buffers must be freed by the caller. JSON responses are `{ok:true,value}` or `{ok:false,error:DomainError}`. The host supplies ISO UTC `now` and owns atomic device-local state/journal persistence, cross-tab CAS, interruption recovery and export/restore. This crate does no persistence itself.

Supported operations:

- `initialize`: `household_id`, `diner_id`, IANA `zone`, local `today`, `now`, optional `demo`. Default is an empty resumable household draft. `demo:true` creates an explicitly synthetic profile and four independent weeks with both privacy defaults off.
- `snapshot`, `validate_state`: `state`, `now`. Restore validation checks exact canonical contracts, projections, archives, selected history, personal candidate admission, original command/response receipts and selection admission against original food inputs.
- `board`: `state`, `now`, optional `week_id`, `slot`, `options`. Options use `overrides`, `extra_recipients`, `make_extra`, `leftover_source`, `eat_by_time` and `time_resolution`.
- `dispatch`: `state`, canonical `command:AppCommandV1`, `command_json` containing the exact originally retained JSON bytes, `now`, optional `today`. Returns `{state,receipt}`. Replays preserve the original response revision/digest. A changed command under an existing ID is refused. The receipt uses the existing `DevelopmentCurrent` UI bridge profile; it does not claim native storage or product qualification.
  The local `suggest_planning_horizon` command names all four current week IDs in chronological order, a `fill_open` or `replace_suggestions` mode and explicit repeat permission. It plans against the evolving draft and retained selected/ordered history, returns one complete state and receipt, and leaves no-fit weeks unchanged. The browser owner commits the whole result once. `swap_named` remains a single-meal command. No AI call, basket change or calendar publication is part of this action.
- `lookup`: the same state/command/command_json binding. Returns `{receipt}` marked replayed.
- `conflicts`: `state`, `now`, zero-based `offset`, `limit` from 1 to 100. Returns `{conflicts,total,offset,next_offset}` across active, disabled and archived selections. Snapshot contains the first 100 deterministically ordered conflicts; the complete count and subsequent pages remain available.
- `prepare_proposal`: `state`, `week_id`, explicit `slots`, `mode`, `allow_repeats`, `now`, optional `nonce:Text`. The browser owner must supply a fresh UUID for every prepare, including after cancellation/restore; the exact nonce participates in the opaque proposal ID so the same context and second cannot resurrect an old returned result. It is not persisted as a new field or included in public context. Omitted nonce preserves the legacy direct-caller ID convention and cannot provide this same-second cancellation protection. Returns `{state,request}` and saves a private scoped proposal journal. The outbound request includes only correlation, scope and recipe references/titles; no household facts, restrictions, diner identities or portions are included. It requires the saved AI privacy switch on.
- `return_proposal`: `state`, `now`, `result:{proposal_id,context_digest,selections:[{slot,recipe}]}`. Exact correlation, current context, scope and food checks materialise saved local choices. Returns `{state,command:AppCommand,status:"review_ready"}` for explicit normal dispatch. It does not apply the returned proposal. New Apply receipts persist `accepted_proposal:{result,result_digest}` within their existing command/response journal. An identical accepted result after reload returns `{state:unchanged,command:null,status:"already_applied"}`; a changed result with the same proposal ID is refused. Identical accepted acknowledgement remains a read-only no-op when AI is subsequently switched off.
- `pending_proposal`: `state`, `now`. Returns `{request,command,status}` for reload recovery. Privacy changes and other committed planner commands revoke the pending scope.
- `revoke_pending_proposal`: `state`, required `now`. Strictly parses and audits the supplied state before returning that state with only `pending_proposal:null`. Snapshot, revisions, history, archives, library, essentials and original receipts (including accepted-result journals) are unchanged. An already idle valid state is returned unchanged, including when AI is off. The browser owner uses this private-journal operation inside its reviewed account/device restore transaction so a backup's prior unapplied request cannot revive in a new user context. The old result/Apply scope is subsequently refused; accepted-result duplicate acknowledgements still return a no-op.

Prepare/return/revoke update the private journal without advancing Snapshot revision; the browser owner's transaction generation must protect these writes. `dispatch` advances Snapshot revision and journals the original response atomically with candidate state. The canonical document bound is 8 MiB; archive/history/receipt bounds are explicit. A refused mutation never supplies partially changed state.

The optional `accepted_proposal` receipt extension is additive: absent or null means an older receipt with no recoverable public AI correlation. Every original required receipt field stays required. Existing pre-Apply review records contain enough saved slot/recipe/correlation data to journal a new Apply correctly. Previously applied receipts without this extension cannot reconstruct a missing proposal ID and are not claimed to support result-level recovery.

`tests/fixtures/archived-conflicts-110.json` is a synthetic engineering fixture generated through 13 actual API commands by the explicitly invoked `conflict_archive` test. It contains five retained weeks and 105 admitted meals, with one week archived after horizon rollover; a later synthetic restriction change exposes 110 complete conflicts in pages of 100 and 10. Its fixed test clock advances from 12 to 19 October 2026, so validation must supply that simulated time or later. It is boundary evidence, not an ordinary current-device household export or production food evidence. Regenerate with `cargo test --manifest-path crates/browser/Cargo.toml --release --locked --test conflict_archive -- --ignored --nocapture`.

For explicitly reviewed local UI recovery QA, `tests/generate-conflict-fixture.mjs` generates a separate kitchen using the actual zero-import WASM `initialize`, `board` and `dispatch` API. Its default simulation clocks are 5 October 2026 at 12:00 UTC and 12 October at 12:00 UTC. They change command inputs before admission; the resulting receipts, response digests, week identities and food projections are computed by the engine. No existing fixture or receipt is patched. It verifies a cold restore against the actual current device clock in a fresh WASM instance and checks all 110 conflicts, both pages and the retained archived week before saving files.

Run `node crates/browser/tests/generate-conflict-fixture.mjs` after building the current WASM module. The optional positional arguments are initial ISO date, rollover ISO date, output fixture basename, and absolute WASM path; the dates must be exactly seven days apart and the final simulated clock must not be in the device future. Defaults produce `tests/fixtures/current-device-conflicts-110.json` (raw engine state) and `tests/fixtures/current-device-conflicts-110-backup.json` (the same state in the existing `mstrchf-device-backup` version 1 reviewed-restore format). Both are clearly synthetic QA material. The generator uses exclusive creation and refuses to overwrite the preserved original fixture; provide a new output basename for a separate run. This supports a reviewed recovery test, not authority to replace anyone's saved kitchen or evidence of observed UI acceptance.

The boundary keeps bounded in-memory caches of already validated immutable state and original receipt food proofs, plus the complete pure conflict projection. Its 256-entry original-week proof cache keys the complete original household profile, privacy policy, week and original supplied clock; it reuses exact original food inputs shared by distinct receipts. Receipt digests, command binding, chronology, history reconstruction and current-state checks remain outside that cache. These caches are never persisted and a fresh WASM instance revalidates saved state.

The final run restored a deeply equal state, returned all 110 conflicts through pages, took 248 ms for a warm Snapshot and 788 ms for the second conflict page, and used 29,163,520 bytes of WASM memory. Its zero-import module was 8,683,502 bytes with SHA-256 `67eb85c11888226fec726ce11ea90fc63af450b97741f21af70ebf746aa7fb10`. The shared contract caches preserve the complete untrusted wire walk and bounded decoder. These are synthetic boundary timings on one machine, not browser responsiveness guarantees. Large cold journals still need computation in a Worker and persistence protected by owner generation CAS.

Manual setup/profile/privacy/week editing, exact choices, suggestions, personal candidate saves, explicit known-packet admission, feedback/hiding, essentials and scoped AI proposal application are supported. Provider jobs, approval/order/calendar mutations and feedback-driven portion changes are explicitly refused until their browser routes are implemented. Engineering recipes remain synthetic; candidates remain outside planning; the exact reviewed R3 porridge packet has a Rust-enforced one-adult fresh-breakfast scope. Each original receipt resolves its chronological catalogue and retains exact snapshot/command digests. Export carries the immutable admitted packet bodies; matching caller digests or actor labels never creates evidence authority.
